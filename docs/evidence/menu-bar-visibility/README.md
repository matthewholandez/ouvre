# Menu bar visibility verification

Verified October 25, 2026 in a graphical macOS session. The app under test was a separately identified Debug clone with a temporary configuration and trace under `/tmp/ouvre-menu-visibility.nqYzQZ`. The system default browser and normal Ouvre configuration were not changed. [Light](general.png) and [dark](general-dark.png) captures show the General control and recovery text.

| Check | Observed result |
| --- | --- |
| Existing configuration | Core test decoded an older version 1 file without `showInMenuBar` as `true`; a saved `false` value survived a round trip. |
| Native Settings switch | The isolated SwiftUI/AppKit harness clicked the switch off and on, then confirmed a read-only model could not hide the item. |
| Immediate visibility | Debug clone trace recorded `menu-bar visible=true`, then `menu-bar visible=false` after the same model setter used by the switch. The temporary JSON held `"showInMenuBar": false`. |
| Link delivery while hidden | LaunchServices delivered `https://example.org/ouvre-menu-hidden?marker=hidden-routing#fragment`; trace recorded `receive`, `process`, and `picker` with the exact URL while the item was hidden. |
| Recovery and persistence | Reopening the running app from its bundle showed Settings with `visible=false`; after restarting only the clone, startup loaded `visible=false`. Reopening it again showed Settings, and restoring the item recorded `visible=true` and saved `true`. |

Automated checks: `swift test --scratch-path /tmp/ouvre-swift-cache` passed 8 tests; `xcodebuild -project Ouvre.xcodeproj -scheme Ouvre -configuration Debug -derivedDataPath /tmp/ouvre-menu-bar-build -arch arm64 CODE_SIGNING_ALLOWED=NO build` succeeded; `scripts/ui/capture.sh /tmp/ouvre-menu-ui --settings-only` and `scripts/ui/capture.sh /tmp/ouvre-menu-ui --interactions-only` passed. The added General row moved the fallback picker below the harness's previous click position; updating that coordinate made the complete interaction check pass. These compiler and UI commands required execution outside the command sandbox on this host because SwiftPM's own sandbox and the SwiftUI macro plugin were blocked there. Actual test output and runtime trace entries are in [checks.txt](checks.txt) and [trace.txt](trace.txt).

To reproduce the isolated app check, build the Debug app, copy it to a temporary `.app`, give the clone a distinct `CFBundleIdentifier`, and add `LSEnvironment` values for `OUVRE_TEST_CONFIG`, `OUVRE_TEST_CHROME_ROOT`, and `OUVRE_TEST_TRACE` as described in [macOS integration verification](../../VERIFICATION.md). Start its config with `{"version":1,"rules":[],"hiddenDestinationIDs":[],"fallback":null,"showInMenuBar":true}`. Launch the signed clone with `open -a`. Write `menu-hide` or `menu-show` to `command.txt` beside the trace, then inspect the `menu-bar visible=` and `menu visible=` entries and the temporary config. While hidden, send a marked HTTPS URL with `open -a /path/to/clone.app URL`; its trace should show `receive`, `process`, and `picker`. Write `dismiss` to `command.txt`, and reopen the app with `open -a /path/to/clone.app` to check the Settings recovery path. Restart only the test clone to check persisted startup behavior.

The native harness checks the actual Settings binding in a preview window; the Debug trace checks status-item visibility in the running clone. Neither check changes the user's default handler. The trace proves Ouvre received and presented the hidden-state link; it does not claim a browser launched for that picker link.
